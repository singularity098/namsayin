# CLAUDE.md

Guidance for Claude when working in this repository. Keep this file up to date: when a decision, convention, command or milestone changes, update it in the same commit.

## Project

Xythos (named NAMsayin until 2026-10-29) is a guitar rig plugin (VST3 + LV2, and AU on macOS) in C++20, built with DPF (plugin framework + NanoVG UI) and NeuralAmpModelerCore.

- **Requirements**: `docs/Requirements.md` — the owner's feature list plus agreed decisions. Treat it as the source of truth; record new decisions there.
- **Architecture and milestones**: `docs/Architecture.md` — design, v1 milestones (M0–M10) and decisions log.
- **Current milestone**: M1, M2 (minus resampling), M3 (delay, reverb, compressor), M5 (library, settings), M6 (split/merge), M7 (presets, undo/redo, MIDI learn), M8 (tuner) and M9 (metronome) are done, and M4 is done (every pedal now has the owner's photo with 2-3 knobs, a power LED and a clickable footswitch on its face, 2026-10-28; the neon placeholder art remains for blocks without an image). The IR loader (local .wav cab IRs) and the Doppelganger Delay (echoes alternate flanger/chorus; `docs/Architecture.md` 4.7b) are also done, at the owner's request, and so is the pedal set, including the second set of 18, six more synths, the Poly Chip (polyphonic chip synth), the third set of 16 (2026-10-23: Sympathetic Strings to Piano, and a Fart pedal), better note tracking (NoteTracker, Track From, Lookahead; the poly finder too, with per-band noise floors so a live input's hiss and hum don't cut notes short, 2026-10-25), MIDI Out (2026-10-24), the DI category (ten bass DI boxes and preamps, 2026-10-24; Architecture 4.11), six compressor pedals (Neve-style diode bridge and console channel, two optical, FET, OTA; 2026-10-29; their photos and a new Noise Gate photo arrived the same day) the Modulation Sweeper (sweeps between 2-3 of chorus/flanger/phaser/vibrato; `docs/Requirements.md` "Pedals", Architecture 4.11; owner's call: no rush to v1) and speaker cabinet photos for IR blocks, picked per IR from its hash and changeable by right-click (2026-10-29), and note tracking down to a 5-string bass's low B (single notes from 28 Hz, the poly finder's bands from B0; 2026-10-29), and (2026-10-30) generic pedal photos for NAM pedal captures and pedals awaiting their render, a Home button in Add Block's library lists, middle-click toggling bypass, and the looper's Count In mode. Next: M10 (v1.0 release: performance, DAW testing, docs).

## Fixed decisions (don't revisit without the owner)

- Formats: VST3 and LV2; on macOS also AU (owner, 2026-10-24: Logic and GarageBand load nothing else). No standalone app, no CLAP.
- Platforms: Linux and Windows, x86-64 only, AVX2/FMA required; macOS 11+ as a universal binary (arm64 + x86_64 with AVX2/FMA; owner, 2026-10-24, was "no macOS, no ARM"). ARM only on macOS. CPU-specific code goes through `src/engine/CpuHints.hpp` (denormal flushing, spin-wait hint).
- Name: Xythos; hosts show the developer as Xythos (`DISTRHO_PLUGIN_BRAND`; owner, 2026-10-29: not their username). The VST3/AU IDs (`S098`, `NMsy`) are from the old name and stay, so saved projects keep finding the plugin (Architecture decisions log 19).
- License: MIT. New source files start with `// SPDX-License-Identifier: MIT` and `// Copyright (c) 2026 singularity098`.
- UI: DPF's NanoVG, very dark theme: the window shows the owner's dark background image (owner, 2026-10-28; `resources/background/`, embedded as WebP by `tools/embed_background.py`, byte for byte as the owner gave it, else re-encoded losslessly: the owner saw artifacts in a lossy one; was plain black, and before that a wood image); everything over it is translucent black at 50% with hairline gray outlines (no gradient; owner, 2026-10-29; was 90%, which let next to nothing of the dark background through): bars, panels, tiles, buttons, tuner and metronome (`theme::panelFill`), and items listed in dialogs at 55% (`itemFill`, `Surface::Item`); except the popups over the chain, which are 95% so they read clearly (owner, 2026-10-29; a blur behind them was tried and dropped): tooltips, dropdown and right-click menus, Add Block, Settings, the other dialogs (Save Preset, Manage Presets, Images, Cab Image) and the toast (`popupFill`, `Surface::Popup`/`Surface::Dialog`; Add Block's items 97%, `popupItemFill`). The rule, owner 2026-10-29: what the window shows in its base state is 50%; everything that appears over it is 95%. The tuner and metronome replace the chain view, so they count as base state), hairline icons. Outlines, buttons, fills and knobs (owner, 2026-10-29): Settings can paint them with a window-wide gradient instead of the highlight colour: Smooth or Splotchy, with 2 or 3 colours. The default is Splotchy in the owner's colours #7278fe, #c688d6, #a85eea (the Iris preset; owner, 2026-10-30); other presets Sunset, Ocean, Mint, Gold, all pale, as are the Solid accent swatches (white first; owner, 2026-10-30: pale reads better on black). The colour picker (Custom…, for the accent or a gradient colour) is a colour wheel (hue around, saturation outward) with a brightness slider, the colour's name (`ink::colorName()`, "pale indigo"), its hex value (a text field: select, copy, type) and the user's saved colours (`Settings::savedColors`). Settings stores these as `highlightStyle`/`highlightColors` (and `accentColor` for a picked accent); the first version's `inkMode`/`inkColors`, never released, are ignored. The logo's crop circle takes the highlight colour (owner, 2026-10-30; was fixed violet): it's its own white layer, tinted when drawn (with a gradient on, the gradient's colour where it sits). Colours must be light (relative luminance ≥ 0.12; `ink::lighten()` lifts darker ones). No animation. Text can't take the gradient: NanoVG's glyphs use the paint's colour alone, so `text()`/`textBox()` draw plain (see `docs/Architecture.md`). `src/state/Ink.*` makes the texture; `XythosUI`'s `fillColor`/`strokeColor` shadow NanoVG's and route the highlight to the window paint. Each chain tile has a white power button top left (`drawPowerButton()`; dim gray while bypassed). Pedals have a power LED, lit while the block is on (`drawLed()`; image LEDs are placed in `PedalFaces.cpp` and drawn from photos, `drawFaceLed()`). Font: Jost Light. The top bar (80 px) shows the logo big (`drawLogo()`, owner 2026-10-29; under ~1000 px wide it shrinks, down to 70%, so the GitHub and Fretbored links still fit). Knobs: tick scale lit to the value, with a dot for the position. Theme tokens are at the top of `src/ui/XythosUI.cpp`. Draw in logical pixels and scale by `getScaleFactor()`.
- Block panel: a large block image on the left (the pedal's photo; drawn placeholder art for blocks without one), generic controls centred in the space to its right and spread out to fill it (owner, 2026-10-28; were right-justified). While the block is bypassed they're dark gray (`dimmed()`), still adjustable. The photo's face knobs turn the same parameters as the generic ones; its footswitch toggles bypass. Face knob names are at most five letters (`faceKnobLabel()`: "Damping" is "Damp"), small (9), and three knobs sit in a shallow triangle, the middle one higher (owner, 2026-10-28).
- Pedal images: Krea-2 renders chosen by the owner. When the owner asks for a new pedal, also write its four image prompts (`docs/PedalImagePrompts.md`), with a glyph unique to that pedal.
- Zero latency by default; only blocks that need latency add it, and it's reported to the host.
- Max 32 blocks; each block keeps a fixed parameter slot for its lifetime (automation/MIDI follow the block).
- One split at a time; branch B may run on a second core.
- v1 scope: local NAM blocks, local IR blocks, delay, Doppelganger Delay, reverb (room/hall/plate), compressor (studio style), plus tuner, metronome, presets, settings, undo/redo.
- Primary test DAW: Reaper.

## Conventions

- **Git: work directly on `main` until v1.0** (the owner's decision: Claude writes nearly all the code, so branches and PRs add little). Commit to `main` and push `main`, even when a session is set up with its own feature branch; no PRs unless the owner asks. Run the tests before every push, since there's no PR CI gate. Revisit after v1.0.

- DPF style: classes in `START_NAMESPACE_DISTRHO`, members prefixed `f` in DPF subclasses, 4-space indent.
- The audio thread (`run()` and everything it calls) must never allocate, lock or touch files. `activate()` and `run()` never overlap (a flag handshake in the plugin), and a non-finite chain output is silenced and makes the plugin rebuild the chain with fresh blocks (`Engine::takeChainFault()`; `docs/Architecture.md` 4.2). Heavy work (model loading, chain rebuilds, tuner analysis) happens on other threads and is handed over lock-free.
- The UI may run in a separate process (LV2), so DSP↔UI communication goes through parameters and state only — no direct pointers.
- `CMAKE_CXX_EXTENSIONS` is ON because DPF's UI code uses `typeof`.
- **Host parameter indices are DAW automation IDs — never reorder or remove them.** Globals come first, then 32 slots × 17 (bypass + 16; was 8, raised before release for the Doppelganger Delay — fixed from v1.0 on). Parameters added later go after the slots (`kFirstLaterParam` in `src/engine/Params.hpp`).
- Slot parameters are normalized 0..1 for the host; each block's `ParamSpec` maps them to real values. `Choice` params list their labels in `ParamSpec::choices`; the UI draws them as a button that opens a dropdown of the choices (owner, 2026-10-24; so does the Lookahead button). `Momentary` params are footswitch actions (the looper's buttons): 1 while held (the UI holds a quick click for 80 ms so the DSP sees it), and the block acts on the 0 -> 1 edge, which also suits MIDI footswitches. With a Latch control a press latches it on inside the block (Kill Switch, Beat Repeat, Tape Stop), which no host parameter holds, so blocks report it (`Block::latched()`, bit i = parameter i; the engine publishes it as the hidden output `slotLatchParam()`) and take it back (`setLatched()`): the chain state stores it as a block's `latched`, filled in by the UI when saving a preset and by the DSP's `getState()` for projects. Loading a preset sends the chain with `restoreLatches`, so blocks the DSP keeps take it too; other chain sends leave kept blocks alone. A block keeps restored bits until Latch is switched from on to off (the host may restore Latch after the chain). The panel lights a latched button.
- When touching the note tracking (mono or poly), run both benchmarks before and after: the synthetic guitar's and the owner's recordings' (`tools/decode_recordings.sh` first). The recordings are what counts; the synthetic guitar has stronger fundamentals than a real DI.
- Pitch-following blocks use `TrackedInput` (Track as their last parameter, the `"lookahead"` config, `BlockDescriptor::lookahead` for the UI's Lookahead button). Track defaults to Rig In (owner, 2026-10-24), but the sound always comes from the block's own input: the note's level and velocity are its input's (`LevelFollower`), so what's before the block still shapes it. Lookahead stays off by default (owner, 2026-10-23). When touching the note tracking, run the benchmark before and after.
- Blocks send MIDI through `Block::setMidiOutput()` (`MidiOutput`: frames are the block's buffer's; the engine handles the timing and ends a block's notes when it's bypassed, removed or rebuilt). The plugin has a MIDI output (`DISTRHO_PLUGIN_WANT_MIDI_OUTPUT`); in Reaper the next plugin in the FX chain receives it.
- Blocks get the host tempo through `Block::setTempo()` and can show a level in the UI through `Block::meter()` (one hidden output parameter per slot, `slotMeterParam()`; the descriptor's `meterName` makes the panel show it). `Block::setRigInput()` gives blocks the chain's input (the noise gate's "Rig In" key).
- Tempo sync is generic: a descriptor's `syncParam`/`syncedParam`/`syncedIsRate` make the UI show note values (`TempoSync.hpp`); the block maps the knob itself. While the host plays, `Block::setSongPosition()` gives the position in quarter notes; synced LFOs lock to it (`Lfo::syncTo`), so they land on the beat.
- A `Choice` parameter's list must never grow or shrink once released: its normalized values would map to other choices in saved projects. Add a new block type instead.
- Every control needs a hover help text in `src/ui/ParamHelp.cpp` (plain English: what it does and how to use it), and so does every block type (`blockTypeHelp()`: what it is, what it's for, where it goes in the chain; shown when hovering a tile or a block in Add Block); `tests/ParamHelpTests.cpp` fails for a block type, block control or global control without one. Help is keyed by typeId and control name, so renaming a control means renaming its help entry.
- `tests/BlockSanityTests.cpp` runs every registered block at default, extreme and random settings (finite, bounded, no allocation, silent for silence). New blocks get behaviour tests too (`tests/PedalTests.cpp`, `tests/MorePedalTests.cpp` for the second set, `tests/SynthTests.cpp` for the synths, `tests/ThirdSetTests.cpp` for the third set, `tests/DiTests.cpp` for the DI boxes, `tests/CompPedalTests.cpp` for the compressor pedals). Every pedal also needs its own face symbol in `src/ui/BlockGlyphs.cpp` (`tests/BlockGlyphTests.cpp`).
- Block `typeId`s are stored in presets and plugin state — never rename one.
- Parameter values live in the host. `ChainState.params`/`bypass` are only for presets and undo; the UI pushes them to the host.
- The chain reaches the DSP as the `chain` state string (JSON). `setState()` runs off the audio thread and builds the new graph there.
- New audio-path code gets a test, including the no-allocation check (`testing::AllocationGuard`).
- No fast-math (`-ffast-math`, `/fp:fast`) and no NaN sentinels: compilers may assume NaN never occurs. A Windows-only test failure came from exactly this. To check, build the tests with `-DCMAKE_CXX_FLAGS=-ffast-math` and run them.

## Notes

- CI fetches submodules with `.github/scripts/fetch-submodules.sh` (retries; skips NAM Core's unused AudioDSPTools) and caches them, because Eigen is hosted on GitLab, which sometimes refuses requests under load.
- NAM Core is linked as a whole archive: it registers model architectures from static initializers, which a normal static link drops.
- NAM Core is built with `NAM_SAMPLE_FLOAT`, so models process `float` directly.
- NAM tests use the models in `deps/NeuralAmpModelerCore/example_models` (`XYTHOS_EXAMPLE_MODELS`).
- The engine reports running slots through two output parameters (`kParamRunningSlotsLow/High`); the UI marks blocks that haven't started 2.5 s after a chain change, and shows a banner if none have.
- **Reaper's LV2 hosting doesn't deliver the UI's state messages to the DSP** (confirmed by the owner; VST3 works). So the chain has a second route: the UI writes it to a per-instance file and bumps the hidden Chain Revision parameter; a DSP thread reads the file (`src/state/ChainExchange.*`). The DSP also keeps the chain itself (`DISTRHO_PLUGIN_WANT_FULL_STATE`) for project save/restore and writes the file so a reopened UI can read it. Test the fallback with a build configured with `-DCMAKE_CXX_FLAGS=-DXYTHOS_TEST_NO_STATE_MESSAGE` (UI never sends the state message) in jalv.
- Looper Count In mode (owner, 2026-10-30; the default): a press starts a count-in (Count-In clicks), records exactly Measures bars of Beats at BPM with the click, closes the loop itself, overdubs Loops - 1 more passes, then plays with no click. The clicks (the metronome's Classic sound, `classicMetronomeClick()`) go to the output only. Loopers saved before it have no `"countIn"` config key and stay in Free mode until the UI migrates them (`kMigrations`). See Architecture "Looper".
- Middle-clicking a block enables or bypasses it (owner, 2026-10-30; it removed it from 2026-10-24).
- Metronome: see `docs/Architecture.md` 4.10. All its settings are host parameters (most hidden), not state, so they reach the DSP in every host. All its sounds are generated in code (`Metronome.cpp`), no samples (owner's decision): Classic is Fretbored's click (a tone with 2nd and 3rd harmonics, 50 ms decay; fitted from the owner's WAVs) raised two semitones at the owner's request (1683.6/1122.5 Hz; Fretbored's is 1500/1000), Digital and Beep are synthesized too. Don't add sample files.
- Block images: the user's own image wins (`BlockState::image`, an id in their amp, cab or pedal library: `images/amps|cabs|pedals/` in the config dir, `src/state/UserImages.*`; NAM blocks use amps, IR blocks cabs, the rest pedals; owner, 2026-10-29, replacing sidecar images next to NAM/IR files). - MIDI learn: the map (CC → host parameter) is part of the chain state, so it travels like the chain and is in undo and presets. - Redraw rate: on Linux the UI can only redraw once per host idle tick (pugl processes X11 events and exposes from the host's idle/timer callback; DPF asks VST3 hosts for 16 ms, LV2 hosts choose their own rate, jalv ~30 Hz). A frame costs well under 1 ms of CPU, so drawing isn't the bottleneck. Windows redraws from the native message loop. The owner saw choppy dragging in Reaper on Linux in both LV2 and VST3. DPF leaves the GL swap interval at the driver default (usually vsync on), so each swap could block the host's GUI thread until the next refresh; the UI now turns vsync off for its window (`src/ui/Vsync.cpp`, GLX). Start the host with `XYTHOS_SHOW_FPS=1` to show a readout (idle ticks/s, frames/s, worst gap, draw time) to see what limits it. The owner's readout in Reaper: idle 36/s, frames 36/s, worst gap 31 ms, draw 0.17 ms, so Reaper's tick rate is the limit. Fix for VST3: `patches/dpf/0001-vst3-x11-event-handler.patch` registers the X11 connection with the host run loop's event handler, so mouse events are handled and redrawn as they arrive (owner: 70-80 frames/s in Reaper with it, on a 120 Hz monitor; was 36; the timer callback also handles events Xlib queued during its redraws, which changed nothing measurable). With a 1000 Hz mouse (readout: mouse 800-900/s) frames stay ~80/s and the worst gap ~21 ms while draws take 0.17 ms, so Reaper seems to dispatch run-loop fd events at only ~80 Hz; going further would mean not drawing on Reaper's thread at all (a render thread in DPF), which is a large, risky change. The readout also shows mouse motion events/s. LV2 has no such mechanism (only the host's idle calls), so in Reaper the VST3 version is the smooth one.
