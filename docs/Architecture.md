# Xythos v1 — Architecture and Milestones

This plan covers version 1 as scoped in [Requirements.md](Requirements.md): local NAM blocks, local IR blocks, a delay block, a reverb block and a compressor block, plus everything around them (chain, split/merge, tuner, metronome, presets, settings). Later features (IR loader, other effect categories) are not built in v1, but the design leaves room for them.

## 3. Signal flow

```
in ─► Input level ─┬─► Chain (up to 32 blocks, optional split A/B → merge) ─► Bass/Mid/Treble ─► Output level ─► (+ metronome) ─► Limiter ─► meters ─► out
                   │
                   └─► boost ─► Tuner analysis (dry input)
```

- **Global bypass** passes the input straight to the output (meters keep running).
- **Tuner mute** silences the guitar path only; the metronome stays audible.
- **Metronome** is mixed in before the limiter, so clicks cannot clip the output.
- **Mono mode** takes the first input and processes one channel, output to both sides. It turns stereo where a mono sound needs to spread (owner, 2026-10-29: a mono guitar with two amps panned apart): after a split's merge, and at a block whose descriptor has `stereo` set (the Delay, for its Stereo and Ping-Pong modes); from there on blocks run on two channels. This is decided by the chain's layout alone (a bypassed stereo block still counts), so blocks never switch channel counts while playing. **Stereo mode** runs every block on two channels; a NAM block then holds two model instances (double CPU, as agreed).

## 4. Engine design

### 4.1 Blocks are modular

Every effect is a subclass of `Block`:

```cpp
struct BlockDescriptor {
    const char* typeId;         // "nam", "delay", "reverb" — stored in presets
    const char* displayName;
    Category category;          // NAM, IR, Delay, Reverb, ... (Add Block dialog)
    ParamSpec params[kParamsPerSlot];
    Block* (*create)();
};

class Block {
public:
    virtual void prepare(double sampleRate, uint32_t maxFrames, int channels) = 0;
    virtual void process(float** io, uint32_t frames) = 0;   // real-time safe
    virtual void setParam(int index, float value) = 0;
    virtual uint32_t latency() const { return 0; }
    virtual void reset() = 0;
    virtual void setTempo(double bpm) {}            // host tempo, before every process()
    virtual float meter() const { return 0; }       // a level the UI shows, e.g. gain reduction
};
```

A block's `meter()` reaches the UI through one output parameter per slot (`kParamSlotMeterBase + slot`).

New effects are added by writing one class and one registry line. Removing an effect is deleting both. The Add Block dialog, parameter names and preset loader all read from the registry.

### 4.2 Real-time safety

The audio thread never allocates, locks, or touches files.

1. Edits (add/move/remove block, change model, split/merge) update the `ChainState` in the UI, which sends it to the DSP as the `chain` plugin state.
2. The DSP's `setState()` (always called off the audio thread) builds a new graph. NAM files are loaded and warmed up there, and blocks that didn't change are reused, so their state (delay tails, reverb tails) carries over.
3. The finished graph is handed to the audio thread through a lock-free single-slot exchange. The audio thread picks it up at the start of a buffer, fades the chain output out over 5 ms, swaps, and fades back in over 5 ms. (A fade out/in rather than a crossfade, because reused blocks can't run in two graphs at once.)
4. The old graph goes back through a lock-free queue and is deleted off the audio thread.

**Host activation.** DPF counts the plugin as active before `activate()` returns, and its VST3 `process()` activates the plugin itself, so a host can run audio while `activate()` re-prepares the engine (hosts call it from different threads; Reaper when an FX is switched off and on). The plugin keeps them apart with two flags (sequentially consistent): `activate()` waits for a `run()` in progress, and `run()` outputs silence while `activate()` prepares. Activation prepares and resets every block, so a block must play on after `prepare()` + `reset()` just as a fresh one does (`tests/BlockSanityTests.cpp` checks every block type). The IR block didn't: FFTConvolver's `reset()` unloads the IR, which silenced any chain with a cab after Reaper switched the FX off and on (2026-10-29); the block's `reset()` now leaves its convolvers alone.

**NaN recovery.** A NaN or infinity stays in every recursive filter for good, which would leave the plugin silent until it's removed. The engine replaces non-finite input samples with silence, silences a non-finite chain output before the tone stack and limiter (resetting those if they ever see one), and reports it (`takeChainFault()`); the plugin's exchange thread then rebuilds the chain with fresh blocks (`forgetBlocks()`, at most once a second).

Parameter changes (knobs, automation, MIDI) don't rebuild anything. They go straight to the block through its slot, with per-parameter smoothing.

Parameter values live in the host. `ChainState` also stores each block's normalized values and bypass, but only for presets and undo: when one is loaded, the UI pushes those values to the host. The DSP always reads the host's values.

### 4.3 Parameter slots (DAW automation and MIDI)

The host sees a fixed parameter list:

- **Global**: input mode, input, bass, middle, treble, output, global bypass, limiter on/off, tuner on/off, tuner mute, metronome on/off, metronome volume, and a few more.
- **32 slots × 17 parameters**: slot bypass plus 16 block parameters (8 until the Doppelganger Delay needed more; changed before release, so no saved automation was affected). That's ~550 slot parameters, which hosts handle fine.

Each block is assigned a free slot when it is created and keeps it for its whole life, so dragging a block to a new position doesn't break automation. Host-facing names are generic ("Slot 05 · P2"). The UI shows real names, and the slot number in the block panel ("Distortion · Slot 05") so users can find it in their DAW; the tile shows the block's category (it showed "S05" until 2026-10-25, owner's request).

**MIDI learn**: right-click any control (or a block tile, for its bypass) → "MIDI Learn", then move a controller. The mapping (CC + channel → host parameter) is stored in the chain state, so it is saved with the project, in presets and in undo, and reaches the DSP by the same routes as the chain. Incoming CCs are applied at the start of each buffer in `run()`. The DSP reports each CC through hidden output parameters: the UI learns from them, and writes mapped values to the host, since LV2 hosts mostly can't take parameter changes from the DSP (in VST3 the DSP also reports them itself). Right-click → "Clear MIDI" removes a mapping; removing a block removes its mappings.

### 4.4 Split, merge and the second core

- The chain has at most one split. `ChainState` keeps the blocks in one list, left to right, plus `split = {begin, end}`: blocks `[begin, end)` run in the two branches, and each of them has a `branch` tag (A or B). Blocks before `begin` run before the split, blocks from `end` on after the merge. A branch may be empty; it then carries the signal unchanged (a parallel dry path). `ChainState` has helpers (`sectionIndices`, `insert`, `remove`, `move`, `addSplit`, `removeSplit`) that keep the range and tags consistent. Removing the split keeps every block: the branches become serial, A then B. The chain JSON went to version 2 for this; version 1 still loads.
- The merge has A/B balance, and a level, pan and phase invert per branch. These are host parameters (`kParamMergeBalance` … `kParamMergeInvertB`), so they can be automated; one set is enough, as there's only one split. Presets save them. Balance keeps both branches at full level in the middle and turns the other one down towards either end. Pan works like a balance control, in Mono mode too (the chain is stereo after the merge; a branch still mono plays on both sides). **Align** (`kParamMergeAlign`, ±5 ms; owner, 2026-10-29: two similar amps summed sounded bad, likely a few samples apart) delays branch B (right) or A (left) by a fractional, smoothed amount (Hermite reads), to line up two amp captures; it adds no reported latency. At 0 it passes the branches through exactly. All merge gains are smoothed, so phase invert fades through zero instead of clicking. Invert A and B are off by default (owner, 2026-10-29: Invert A was on for a while, but out-of-phase captures aren't common); a new split resets the merge controls to their defaults.
- If the two branches have different latencies, the shorter branch is delayed to match (`DelayLine`), and the host is told the longer one.
- **Parallel processing** (on by default; Settings > Parallel processing. The DSP reads the setting when it builds a chain, and the UI resends the chain when it changes): a `ParallelWorker` thread is woken each buffer to run branch B while the audio thread runs branch A, and the audio thread then waits for it. Waking is lock-free (an atomic counter with `wait`/`notify_one`), and the audio thread spins briefly, then yields, until the worker is done. The worker copies the audio thread's scheduling policy and priority on its first job (Linux), or uses `THREAD_PRIORITY_TIME_CRITICAL` (Windows), and flushes denormals like a host audio thread. If the worker is late, the audio thread keeps waiting (no extra latency, but a risk of a dropout on an overloaded machine). With the toggle off, or with an empty branch B, both branches run in sequence on the audio thread. The worker thread is only started once a chain needs it.
- UI: with a split, the chain view has two rows of slightly smaller tiles: branch A and everything outside the split on the top row, branch B below, and a tall merge tile where they join (click it for the merge controls, × to remove the split). Each branch and the part after the merge has its own "+".  While there's no split, hovering the gap before a block (or before the "+") shows a small split icon on the signal line; clicking it adds an empty split there (both branches start empty). Blocks are dragged between rows and sections freely; a line in the highlight colour shows where a block will land.

### 4.5 Latency

- All v1 blocks are zero latency by default. The engine adds up block latencies along the path, aligns branches, and reports the total to the host (DPF `setLatency`). The pitch-following blocks can add latency with their Lookahead (4.11, "Note tracking"). A bypassed block with latency still delays its signal (`Node::bypassDelay`), so bypassing it doesn't change the timing or the reported latency.
- **Sample rate**: NAM models record the rate they were trained at, usually 48 kHz. If the host runs at that rate, there's no resampling. Otherwise the NAM block resamples with a low-latency resampler (a few samples), reports that latency, and shows a small warning badge on the block.

### 4.6 The NAM block

- Loads A1 and A2 files through NeuralAmpModelerCore (pinned to v0.6.0, which includes the A2 fast path). Full/Lite is selected with `nam::SlimmableModel::SetSlimmableSize` (1.0 = Full, 0.0 = Lite); it isn't real-time safe, so it's applied off the audio thread.
- A2 size: global default from Settings, with a per-block override.
- Normalization (per-block toggle): uses the loudness value stored in the `.nam` metadata to bring models to a common level. Models with no loudness value are left as they are, with a badge saying so.
- Block parameters: input gain, output gain, normalization on/off, A2 size (Full/Lite).

### 4.7 Delay block

Parameters: time (ms, or a note value when synced), tempo sync on/off, feedback, mix, tone (low-pass in the feedback path), mode (mono / stereo / ping-pong), stereo spread, modulation depth. In stereo mode, left and right have separate lines, offset by the spread setting.

- Time changes glide (a smoothed, fractionally read delay time), like a tape or analog delay, instead of clicking.
- Synced, the Time knob picks from 14 note values (1/1 down to 1/32, with dotted and triplet values); the host tempo comes from DPF's `TimePosition`, 120 BPM when the host doesn't report one. Max delay is 4 s.
- The feedback path has a fixed 40 Hz high-pass, the Tone low-pass and a soft limit above half scale, so 100% feedback stays bounded.
- Ping-pong: the input (summed to mono) enters on the left, repeats alternate left and right.
- Mix: the dry signal stays at full level up to 50%, and the wet signal reaches full level at 50% (also used by the reverb).

### 4.7b Doppelganger Delay block

The owner's idea: a delay whose echoes alternate between two effects. With the default order, echoes 1, 3, 5… are flanged and echoes 2, 4, 6… are chorused, and each echo has only its own effect (they don't stack).

- An ordinary feedback delay keeps every echo in one loop, so effects in the loop would pile up. Instead, one clean line repeats at 2T with feedback g²: `s(t) = x(t) + g² F² s(t−2T)`. Reading it at T gives the odd echoes, `g F s(t−T)`; the loop's own feedback term gives the even ones. These are exactly the echoes of a delay with time T and feedback g, split by parity, so each stream goes through its own effect outside the loop. F is the Tone low-pass (and a 40 Hz high-pass), once per repeat, so repeats darken like the Delay block's.
- Flanger: a 0.25–5.25 ms swept delay with regeneration (−95…95%), level-compensated. Chorus: 1–3 voices around 10 ms, spread evenly around the LFO cycle. Each has rate, depth and mix (0% = clean echoes).
- Order swaps which effect gets the odd echoes. Width offsets the right channel's LFOs (up to 180° for the flanger, 90° for the chorus). Bounce leans flanged echoes left and chorused echoes right (stereo mode).
- Time, Sync, Feedback and Mix work as in the Delay block (same note values; synced up to 4 s, so the line holds 8 s).
- 16 parameters: time, sync, feedback, mix, tone, order, width, bounce, then flange rate/depth/regen/mix and chorus rate/depth/voices/mix.

### 4.8 Reverb block

An algorithmic reverb written in-house (Dattorro-style plate/hall network). Parameters: type (room / hall / plate), decay, pre-delay, damping, low cut, high cut, width, mix. Mono input gives a stereo-wide tail when the plugin is in stereo mode.

- One figure-eight tank (Dattorro 1997) voiced three ways: Plate is the original sizes; Hall scales the tank by 1.45 with deeper, slower modulation; Room scales it to 0.42 with less diffusion and adds early reflections tapped from the pre-delay line.
- Decay is the RT60 in seconds; the tank's decay gain is computed from it and the tank's loop time, so the set time holds for every type and sample rate (tested).
- Buffers are sized for the largest voicing in `prepare()`, so changing type on the audio thread only changes read positions.

### 4.8b Compressor block

Added to v1 at the owner's request. Studio style, feed-forward: stereo-linked peak detector, soft-knee gain computer, attack/release smoothing of the gain in dB, then makeup gain and a dry/wet mix for parallel compression. Parameters: threshold, ratio, attack, release, knee, makeup, mix. Its gain reduction is shown in the block panel through the block meter.

### 4.9 Tuner

- The input (after the Input level, before the chain) is copied into a lock-free ring buffer, and the analysis runs on a DSP-side thread every 20 ms while the tuner is on, never on the audio thread (`engine/tuner/Tuner`). Stereo input is analysed as the sum of both channels.
- The detector doesn't depend on the level, so quiet inputs work as well as loud ones (this is what the "boost" in the signal flow stands for): only a gate at -74 dBFS RMS decides whether there's anything to analyse.
- Pitch detection (`engine/tuner/PitchDetector`): McLeod Pitch Method (as in Fretbored) on an ~85 ms window (4096 samples at 48 kHz, enough for 31 Hz), FFT autocorrelation and parabolic peak interpolation, which on its own is good to about ±0.4 cent. It is then refined: a Hann-weighted normalized cross-correlation over a whole number of periods, low-passed above the 6th harmonic, measured at the largest multiple of the period that fits and divided back. The refinement uses up to four windows of audio (~340 ms) when the note has been steady that long, which makes it far less sensitive to noise.
- Only audio at a steady level is analysed: levels are compared in chunks of whole periods, and a window that isn't steady (a note starting, stopping or changing) gives no reading at all, rather than a wrong one. The UI keeps showing the last note for a second.
- The detected frequency and clarity are output parameters, so this works when an LV2 host runs the UI in a separate process. The UI takes the median of the last five readings (starting over when the note clearly changes) and works out the note and cents from the reference pitch. Traditional (needle, ±50 cents, green within ±2 cents) and strobe (three rows of bands for the fundamental and two octaves, drifting at a speed proportional to the error) views are drawn in the UI; the view is a hidden parameter, so it's saved with the project.
- While the tuner is on, the guitar is muted by default (Tuner Mute; also in global bypass); the metronome stays audible.
- Reference pitch A4 is adjustable from 415 to 466 Hz.
- **Accuracy target: ±0.1 cent from 31 Hz up to the 24th fret of the high E string (~1319 Hz)**, checked by tests at 44.1, 48 and 96 kHz on every half semitone, with pure tones, harmonic-rich tones and noisy tones with a weak fundamental (worst case about 0.01 cent), and through the start and end of notes (a gated tone; a plucked-string-like note whose harmonics decay at different rates). No recorded signals yet: the tests are synthetic.

### 4.10 Metronome

- Runs in the DSP (`engine/metronome/Metronome`), scheduled to the exact sample: each beat's time is kept as a fractional sample position and rounded, so the tempo never drifts, whatever the buffer size. Clicks are mixed in after the Output level and before the limiter, so they can't clip the output; the tuner's mute doesn't silence them. Global bypass does (it's a true bypass).
- **Free mode** (default): its own tempo, starting on beat 1 when switched on. Switching off lets the click that's sounding play out (cutting it would pop).
- **DAW sync** (switch): follows the host's tempo, time signature and transport position (DPF `TimePosition`): clicks fall where the host's beat position crosses a beat or subdivision, only while the transport plays. Each click has an ID (beat × 16 + subdivision), so a click on a buffer boundary is never played twice or missed, and a jump (loop, locate) starts over at the new position. The tempo trainer doesn't apply in sync mode (the host sets the tempo); the gap trainer does, on the host's bars.
- Features match Fretbored: 20–300 BPM (slider, ±1/±5, keyboard), tap tempo, 1–16 beats over 2/4/8/16 with beat grouping (cycled through every split into 2s and 3s; the default follows Fretbored, e.g. 7/8 = 2+2+3), per-beat accents (accent/normal/soft/mute, set by the grouping and by clicking a beat), the eleven subdivisions, Classic/Digital/Beep sounds with separate volume for subdivisions, step and gradual tempo trainer (also slowing down), gap trainer, and a visual pulse (the pendulum sweep was removed at the owner's request, 2026-10-23: at host redraw rates it looked choppy). Fretbored's "visual sync" offset (for Bluetooth speakers) isn't needed in a plugin.
- **Every setting is a host parameter** (tempo, volume, on/off and sync are automatable; the rest are hidden), so it works the same in every host — including Reaper's LV2, which doesn't deliver UI state messages — and is saved with the project. The accents are 16 parameters; the grouping is a bit mask of the beats that start a group, kept only for the UI. The DSP reports the beat being heard, a beat counter (the UI pulses when it changes), the bar, the tempo being played and the gap trainer's mute as output parameters.
- **Panel**: the top bar's Metronome button switches it on and off (and flashes on every beat); ▾ next to it opens the panel, which covers the chain while it's open. Shortcuts while the panel is open (so only while the plugin window has the keyboard focus): Space start/stop, ↑/↓ tempo (Shift: 5 BPM), T tap.
- Sounds: all generated in code at the host rate, no samples (owner's decision, 2026-10-23, so every sound is our own). Classic recreates Fretbored's click, which turned out to be a formula: fitting the owner's two WAVs gave exactly e^(-t/50 ms) (0.5 sin wt + 0.15 sin 2wt + 0.05 sin 3wt), 50 ms long, at 1500 Hz (accent) and 1000 Hz (beat and subdivisions), with zero residual; with the same 0.5 ms / 6 ms edge fades the generated clicks matched the old samples to -56 dB (16-bit rounding). The owner then raised it two semitones (2026-10-26): 1683.6 and 1122.5 Hz. Digital (a short band-limited square wave) and Beep were already generated in code.
- The top bar also has the Fretbored link (opens the web app in the default browser: `xdg-open` / `ShellExecute`).

**The DI category** (2026-10-24, the owner: bass DI boxes; asked whether they are easier than guitar amps: yes, a few stages each, so they're built, not captured; `blocks/DiBlocks.*`, tests in `tests/DiTests.cpp`). A shared base (`DiBase`): every knob smoothed in its own units and the filters (and gains) redesigned every 32 samples while one glides, two 4x oversamplers and a 10 Hz DC blocker per channel. The tube stage is `x / sqrt(1 + x^2)` with different headroom on each half (1 and 0.6) around a 0.15 bias, so it has even harmonics and no output for no input. A bass speaker voicing (45 Hz high-pass, +3 dB at 110 Hz, -4 dB at 450 Hz, two low-passes at 4.5 and 5.5 kHz) and an optical compressor cell (peak detector, 6 dB soft knee, a release that is 65% an 80 ms part and 35% a 1.5 s part) are shared. **Studio DI**: a passive transformer DI: the lows under 150 Hz (12 dB/oct split) go through a slightly asymmetric curve driven up to 30x by Iron, and replace the clean lows in proportion (a core saturates on the lows first); On the recordings: missing note time 19.5 to 15.6 s (in no octave 5.8 to 4.8 s), missed 5 to 4, strays 187 to 186 (6.1 to 7.4 s, mostly notes ending up to 40 ms late, which the Poly Chip's release covers anyway); with the hiss and hum 25.6 to 15.4 s missing, missed 8 to 4. On the synthetic benchmark extra time 4.0 to 6.4 s, the same misses and dropouts. Tried: a lower level bar (the first partials within 9 dB of the loudest band) for playing notes (little gain once the flicker was fixed).
- **Mono tracking on real playing** (2026-10-24, same recordings): the NoteTracker played chords an octave below their root (B1 under a B5, D2 under the open D, C2 under the C5): a power chord's root and fifth (and a major chord's third) repeat together every two root periods, which YIN finds, with nothing at that frequency. The PitchTracker now checks pitches under 200 Hz: over the last two periods (Hann window, so the harmonics fall on whole bins), when the 2nd and 3rd harmonics are within 14 dB of each other and the 1st is 26 dB under them, the pitch is the root, an octave up. On the recordings: stray notes 146 to 128 (15.6 to 6.7 s; an octave or a fifth below a note 13.0 to 4.1 s), missing time 19.8 to 13.5 s; the synthetic benchmark unchanged. 20 dB did a little better on the recordings but moved a synthetic pluck with a weak fundamental (PedalTests) up an octave. What's left is mostly chords, which a mono tracker can't follow (an E5's common period is below the guitar), and the 16th-note chugging riff.
- **Note tracking** (2026-10-23, owner's report: notes played that weren't, notes missed): the mono synths, Harmonizer and Octave follow notes with `dsp/NoteTracker.hpp` (4.11 DSP notes) through `blocks/TrackedInput.hpp`, which adds **Track** (Block In / Rig In: the rig's input is the clean guitar, much easier to follow after an amp or drive; the Poly Chip has it too) as each block's last parameter, and the **Lookahead** block config (`"lookahead"`, ms, 0 by default; the panel's Lookahead button opens a menu of Off, 5, 10, 15, 20, 30). With lookahead the block delays its own audio to match and reports the latency; the owner keeps it off by default until trying it. The benchmark (`tests/TrackingTests.cpp`, `XYTHOS_TRACKING_BENCH=1 ./build/xythos-tests -tc="tracking benchmark"`) plays a synthetic guitar (`tests/GuitarSignals.hpp`: six Karplus-Strong strings with a pick shape, mutes, palm mutes, hammer-ons, bends, strings left ringing, hum and hiss; optionally through a high-gain amp) and scores missed notes, note delay, wrong-pitch and phantom stretches (audible, 3 ms or longer) and dropouts. Over 121 notes: the old tracking (PitchTracker + Pick Filter off) had 165 wrong-pitch stretches (3.0 s) and 56 phantom ones (6.7 s: every muted note rang on about 115 ms); the NoteTracker has about 40 wrong (0.8 s, most of them in an arpeggio left ringing, which no mono tracker can follow) and 5 phantom (0.04 s), median delay 12 ms (old: 8 ms), and with 15 ms lookahead a median delay of 2 ms. After an amp, Rig In scores as well as the clean guitar. Second round (2026-10-24, owner's recordings: chirps at the picks, notes chopped up): on real playing the chirps were the tracker locking onto a harmonic or a subharmonic for a few ms while the pick (or a finger) stops the string, with the level falling fast. Now a doubtful new pitch (aperiodicity over 0.1 without a pick, within 0.4 semitones of 2, 3 or 4 times or a 2nd, 3rd or 4th of the note before, or over an octave from it) needs three estimates in a row instead of two; a new pitch without a pick needs the level at least half the last 32 ms' peak; and other pitches end the playing note only once a new one is confirmed (or after four estimates). Benchmark: 25 wrong (was 40), dropouts 0.41 s (was 0.70), 4 missed (was 3: a note in the ringing arpeggio), delays about the same. Rig In is the default Track; the block's own input (delayed with the lookahead) sets the note's level and scales its velocity (`LevelFollower` in `TrackedInput.hpp`; the Poly Chip scales its voices the same way), so the sound follows the signal path.
- **Robot Filter**: an SVF whose cutoff jumps to a new held value on each clock tick (random, a fixed 8-step random loop, or the input level), with a glide on the octave position. **Talk Box**: three SVF band-passes on the first three formants, interpolated (on a log scale) along a vowel path.

**Modulation Sweeper** (the owner's idea, 2026-10-23): two or three of chorus, flanger, phaser and vibrato, picked by the user (Effect 3 can be None), that the block moves between. Each Sweep Rate step it moves on to the next effect in the pattern (Back & Forth: 1 2 3 2 1..., Cycle: 1 2 3 1...); Glide is the share of each step spent crossfading (raised-cosine, gains adding to 1 because the effects all carry the dry signal; never shorter than 15 ms, so 0% doesn't click). Sync makes each step a note value, counted from the song's start, so moves land on the beat. All four effects run all the time (a two-voice chorus and the vibrato share one input delay line; the flanger has its own feedback line; a 6-stage phaser), so a crossfade never starts from a cold line, and each effect's weight is smoothed (10 ms) so changing the effects or pattern doesn't click. Depth, Mix, Feedback and Width are shared; each effect has its own rate. 15 controls.

Shared DSP (`src/engine/dsp/`):

- **Oversampler**: the drives clip at 4x through polyphase IIR half-band filters (HIIR-style allpass pairs designed in code): flat to 0.49 fs, aliases more than 70 dB down, no added latency (IIR group delay only). Clipping curves are in `Waveshapers.hpp` (x / (1 + |x|^n)^(1/n), square roots only).
- **Svf**: TPT state variable filter, stable when the cutoff moves every sample (wahs, auto wah, filter, synth). `OnePole` and `EnvelopeFollower` live with it.
- **Lfo** (phase accumulator, any phase offset for stereo) and **RandomLfo** (smoothed random, for drift). `TempoSync.hpp` maps a synced knob to a note value: a time knob has the longest note at the top (1/1 down to 1/32); a rate knob has its own list from 4 bars and 2 bars down to 1/32, the fastest at the top. The descriptor's `syncParam`/`syncedParam`/`syncedIsRate` tell the UI.
- **PitchShifter**: delay-line voices, two Hann-crossfaded taps whose delays move at (1 - ratio) samples per sample and jump by the window at the end of a sweep. Polyphonic, no reported latency; the shifted sound trails by about half the window (the Window control). The splices are made phase-coherent: a **PeriodFinder** (autocorrelation on a 12 kHz copy, every 8 ms, lags 7-60 ms, parabolic peak) finds the signal's repetition period, which for chords is their approximate common period (two root periods for a power chord, four for a major triad); the tracked note is the fallback. The window becomes a whole, even number of that period, each tap takes the new window when it jumps, and each jump is steered (a few percent of the window per jump, so it never clicks) to land exactly half a window from the other tap. Shifted notes and chords then keep 95-100% of their energy at the shifted partials (tested; it was 0-20% with a plain window, which is the warble cheap pitch shifters have). Costs about 2-3% of a core per pitch block in stereo. Used by Pitch Shifter, Whammy, Poly Octave, Harmonizer and Shimmer (Shimmer keeps a plain window: its reverb tail has no period).
- **PitchTracker**: YIN (cumulative-mean normalized difference, absolute threshold) on a copy decimated to 12 kHz, every 4 ms, 28-1500 Hz (60 Hz until 2026-10-29, which missed a 7-string's drop A; now down to a 5-string bass's low B, 31 Hz, at the owner's request), then refined at the full rate around the estimate. The difference at each lag is over a window of one lag (at least 2 ms; it was a fixed 17 ms), so an estimate needs about two periods of the note, and it is divided by the two windows' energy, so a fast swell or decay (a pick attack, a palm mute) doesn't read as unclear. On plucked strings (Karplus-Strong, whose fundamental is often weaker than its harmonics) it holds the note to 0.1 cent (tested). It replaced a zero-crossing tracker that locked onto harmonics of low plucked notes. A pitch under 60 Hz needs its fundamental within 9 dB of its 2nd to 4th harmonics: strings left ringing together repeat at their notes' lowest common period, often down there, with nothing at it. The difference function runs over a copy of the newest samples with running sums of squares (cheaper than before at twice the range: about 1% of a core for the NoteTracker). In the NoteTracker, a new note at the mains' 50 or 60 Hz (within 0.2 semitones) needs a pick, so hum after an amp doesn't start notes in the silence. Used through the NoteTracker by the synths, the Harmonizer and the Octave, and directly, as a fallback to the PeriodFinder, by the pitch-synchronous windows.
- **NoteTracker** (2026-10-23; the owner found the synths, pitch pedals and octaver playing notes not played and missing notes): turns the PitchTracker's estimates into notes. Its own level follower holds for a period and then falls fast (the tracker's released over 80 ms, so notes ran on past every mute); the gate opens 12 dB over a followed noise floor (rising only between notes) and closes 50 dB under the note's peak; a level 20 dB under a 20 ms follower is a mute, and the muted tail can't start a note again. A note starts when two estimates in a row agree, with an aperiodicity under 0.3; once it plays, estimates within 0.6 semitone follow it however unclear (bends, vibrato, the decay). Two clear estimates of another pitch end it (a new note without a detected pick); 35 ms without a clear pitch ends it too. A pick (OnsetDetector on the level, or on the level high-passed at 2 kHz, where the pick's click stands out while an old note rings) ends the note before it; it may start a new note only once confirmed by the average level (3 ms) rising 1.25x or holding over 0.3 of its level for 12 ms: a mute clicks too (a finger landing, or the synthetic string's step), and then the level falls, so the click counts as a mute and the tail can't start a note (the average, because the peak follower holds a click's spike). With it the benchmark's phantom notes went from 5 to 0. The Pick Filter: a new note must also hold that long. **Lookahead**: the output runs that far behind the input, and a new note is written back to its pick (or to 8 ms before its first estimate), so notes start on time at the pitch found after the pick.
- **Fdn**: 8-line Householder feedback delay network with input diffusers, per-line damping and RT60 gains, two modulated lines; it can freeze (lossless loop, input shut). Used by Shimmer, Freeze, Bloom Reverb and Gated Reverb.
- **OnsetDetector**: a new pick attack (a fast envelope jumping to twice a slower one, over -50 dB, at most every 60 ms). Used by the Organ, the Sustainer, Bloom Reverb and the NoteTracker.

Notes:

- **Levels**: default settings stay within a few dB of bypass (drives a few dB louder, like a pedal set at unity-plus).
- **Beat-locked LFOs**: while the host's transport plays, the engine passes each block the song position (quarter notes, at the start of each chunk) through `Block::setSongPosition()`. Synced tremolo, flanger, phaser and filter lock their LFO phase to it (cycles counted from the song's start; the tremolo's loudest point lands on the beat), only correcting when off by more than 0.1% of a cycle. Stopped, they run free at the synced rate.
- **Noise gate key**: `Block::setRigInput()` gives every block the chain input (after the input level). With Key = Rig In, a gate after an amp opens and closes on the clean guitar.
- **Momentary parameters** (`ParamScale::Momentary`, the looper's Rec/Dub, Play/Stop, Clear): 1 while held; blocks act on the 0 → 1 edge, so a MIDI footswitch's press/release maps directly. The UI holds a quick click for 80 ms so the press can't fall inside one audio buffer with its release.
- **Looper**: a fixed buffer of 60 s at 48 kHz per channel (23 MB), allocated in `prepare()`. Its status (state, length, position) is encoded in the block meter (`LooperStatus`) and drawn in the panel (`MeterStyle::Looper`). The loop survives chain edits (the engine reuses the block) but not a sample-rate change.
- **Spring reverb**: two springs, each a loop of 60 stretched first-order allpasses (the dispersion that makes the chirp), the transit delay and damping; after Välimäki, Parker and Abel (2010), simplified.
- **Tests**: `tests/BlockSanityTests.cpp` runs every registered block at default, extreme and random settings, at 44.1/48/96 kHz, mono and stereo (finite, bounded, no allocation, silent for silence), and for ten seconds at its maximum to check that no feedback loop grows once the input stops. `tests/PedalTests.cpp` and `tests/DriveTests.cpp` check each pedal's behaviour (gains, notches, rates, intervals, aliasing, looper actions).
- Voicing is by measurement, not by ear; the owner tunes the sound.

## 5. Plugin state, presets and settings

- **Plugin state** (saved by the DAW with the project): a JSON string through DPF's state API, holding the chain, slots, split, block settings, MIDI mappings and metronome settings. File references store the path and the content hash.
- **Preset files** (`.xythos`): a zip containing `preset.json` (the chain, its MIDI map and the global sound controls) and, when exported with "embed files" on (default on), the NAM files and IRs it uses, under `files/<content hash>/`, and the user's images its blocks use, under `images/<amps|cabs|pedals>/<id>` (added to the user's libraries when it's opened: an identical image is reused, a name taken by other content gets a number and the blocks follow). Save and Save As keep presets in the preset folder (`presets/` in the config dir, with subfolders), without files, through an in-app dialog; Export writes an embedded copy anywhere through the system dialog; Open File… opens one from anywhere. Manage Presets… loads saved presets, marks one as the default, which new plugin instances load, and deletes them (Delete asks "Delete?" and deletes on a second click; only preset files inside the preset folder, `deletePreset()`). The top menu has New, Save, Save As, Manage Presets…, Open File…, Export…, the embed option, and every saved preset laid out as the preset folder is: top-level presets first, then each folder as an indented heading with its presets and subfolders under it (the open preset in the highlight colour, the default marked). It scrolls when it's taller than the window. The preset name shows in the top bar, with a dot when the chain has changed since it was saved or opened.
- **Missing files**: on load, each block's file is looked for at its original path, then as an embedded copy (extracted to the cache), then in the library by content hash. If none is found, the block is created grayed out (passes audio through) with "Locate…", and "Use … from the library" when a library file with the same hash appears later.
- **Settings and favorites**: one JSON file per user — `~/.config/xythos/settings.json` on Linux, `%APPDATA%\Xythos\settings.json` on Windows. It's written atomically, and every open instance reloads it when it changes (the UI checks its modification time once a second; a change re-reads the file before saving, so instances don't overwrite each other's changes). Fields: NAM folder, IR folder, default A2 size, normalization default for new blocks, multi-core splits, accent colour (stored as an index into the colour list, which keeps its order; Settings shows white, the default, first), text & outlines mode and its 2-3 colours (`inkMode`, `inkColors` as hex; Sunset to start), favorites. A `blockArt` key from older versions is ignored. Also the update check on/off and the dismissed release (`checkUpdates`, `dismissedUpdate`).
- **Update check** (`src/state/UpdateCheck.*`): while it's on (Settings, default on), the UI checks a few seconds after opening, at most once a day for all instances together (`update-check.json` in the cache dir: when the last check started and the latest version found; claimed before fetching, so instances opening together don't all check, and a failed check also waits a day). `UpdateChecker` fetches GitHub's `releases/latest` (drafts and pre-releases excluded; tags like `v1.2.0`) on its own thread through `HttpGet` (`src/ui/HttpGet.*`: WinHTTP on Windows; the `curl` command on macOS and Linux, so the plugin links no TLS library, HTTPS only), cancelled and joined when the UI closes. A newer version than this build (`XYTHOS_VERSION`, the CMake project version, which `getVersion()` also reports) shows as a notice after Redo in the top bar; clicking opens the releases page (a fixed URL, never one from the response), × stores the version as dismissed. Nothing is downloaded or installed.
- **Favorites** are stored by content hash (XXH3-128 of the file bytes).
- **Undo/redo**: a stack of `ChainState` snapshots (small, so snapshots are cheap), up to 200 steps. One knob gesture is one step. It covers blocks, block values, bypass, the MIDI map and preset loads, not the global knobs. Undo/Redo buttons in the top bar; Ctrl+Z, Ctrl+Shift+Z and Ctrl+Y while the window has focus.

## 6. Library

- Scans the NAM directory and the IR directory on a background thread (`LibraryScanner`), including inside `.zip` files. Files inside zips are addressed as `archive.zip!/folder/model.nam`. When a block uses one, the file is extracted to the cache directory (`cache/extracted/`) off the audio thread and loaded from there.
- An index cache per kind (path, size, modification time, hash, metadata) keeps rescans fast. Only new or changed files are read and hashed. A rescan runs when the UI opens, when a folder changes, and from the Rescan button.
- NAM metadata (gear make/model) is shown under each model in the list, with its gear type and architecture (`describeNamFile()`, `namGear()` in `src/state/Library.*`). Gear types are NAM's trainer's (amp, pedal, pedal_amp, amp_cab, amp_pedal_cab, preamp, studio) and TONE3000's (amp, amp-cab, pedal, outboard, cab, space, experimental; older full-rig, ir), shown as Amp + Cab, Amp Head, Cabinet, Pedal, Outboard, Spaces, Experimental (studio counts as Outboard, preamp and pedal_amp as Amp Head). Architecture: SlimmableContainer, or a WaveNet with one slimmable or per-layer-kernel layer array, is A2; a two-array WaveNet is A1, named by its channels (16/8 Standard, 12/6 Lite, 8/4 Feather, 4/2 Nano); others by their architecture name (LSTM, ConvNet). The index cache stores both (index version 2; older indexes are rescanned). The tile and panel show them too, read from the library, or from the file for one outside it, and warn (amber, with a sign) when an Amp + Cab model has an active cab (IR block or a Cabinet model) after it on any path, or an Amp Head model lacks one on some path (a split's branches are separate paths).
- **User images** (owner, 2026-10-29; replaced sidecar images, `My Amp.png` next to `My Amp.nam`): the user's own images live in three libraries in the config dir, `images/amps/` (NAM blocks), `images/cabs/` (IR blocks) and `images/pedals/` (every other block) (`src/state/UserImages.*`). A block that uses one stores its file name there as its id (`BlockState::image`, `"image"` in the chain JSON, outside `config` so the DSP never rebuilds a block for it; undoable like any chain edit). The block panel's Image… button opens the Images dialog: the stock image and the library's images as tiles; a click picks one, Add Image… copies a file in through the file browser (8-bit PNG, JPEG or WebP, checked by its first bytes; an image with the same content is reused, a taken name gets " 2"), Delete asks "Delete?" and deletes on a second click. They're shown on the tile and in the block panel as they are, with no face knobs, LED or footswitch. A deleted image's blocks keep the id and show their stock look (so a preset saved with it still loads). Otherwise the block type's built-in image (`resources/blocks/<typeId>.webp`, cropped from the owner's photo by `tools/prepare_block_image.py`; tiles and lists use `resources/blocks/thumbs/<typeId>.webp`. These are the only copy in git: `cmake/EmbedBlockImages.cmake` turns them into `BlockImages.cpp` in the build directory. They were about 30 KB each (640 px, q88); since 2026-10-28 they're WebPs (decoded with libwebp in `src/ui/WebpImage.*`, as DPF's stb_image reads only PNG and JPEG) 1280 px high at q96, about 115 KB each (11 MB for all, thumbnails included), and still stay inside the plugin: a file next to it would be one more thing to lose when copying a plugin, and embedded data costs no RAM until it's read (the loader maps it lazily). The UI decodes a full image when it's first drawn and frees the least recently drawn beyond four; thumbnails stay loaded), otherwise the placeholder art (`drawBlockArt()`: the Neon style, black enclosures outlined in glowing lines of the category colour; each pedal has its own symbol on its face, drawn from its name and purpose: `src/ui/BlockGlyphs.*`, plain polylines and dots in the pedal's 124x200 frame, so `tests/BlockGlyphTests.cpp` can check that every pedal has one and no two are the same; a type without one falls back to its category's symbol). NAM and IR blocks get a look per file from its path (`src/ui/FileLooks.*`: FNV-1a + splitmix64 over the path string, fixed so it's the same in every build; empty for the generic look in Add Block; cabs stay 2x2), checked by `tests/FileLookTests.cpp`; changing the mapping changes how everyone's files look, so don't without reason. **Cab images** (owner, 2026-10-29): IR blocks show a built-in speaker cabinet photo instead (`resources/cabs/<size>-<n>.webp` and `thumbs/`, by `tools/prepare_cab_images.py`; embedded as `CabImages.cpp` by the same CMake script with `-DKIND=Cab`; `builtinCabImage()`, `builtinCabThumb()`, `builtinCabIds()`; the UI caches them with the block images under `cab:<id>`). `defaultCabImage()` (FileLooks) picks one from the IR's content hash with the same dice, among the size its file name gives if it gives one of the six; the user's pick (the Cab Image dialog: right-click an IR in Add Block, the panel's cab image, or the tile menu) is stored in `Settings::cabImages`, content hash -> id, so it follows the file into every chain and preset and syncs to every instance like the other settings. Closing the dialog opened from Add Block goes back to Add Block. A user image (`BlockState::image`) still wins. User images: 8-bit PNG, JPEG or WebP (DPF's stb_image doesn't decode 16-bit PNG; WebP goes through libwebp). **Face knobs** (proof of concept on the Poly Chip, 2026-10-25): `src/ui/PedalFaces.*` lists, per typeId, knobs on its built-in image (parameter name, centre and radius as fractions of the image; checked by `tests/PedalFaceTests.cpp`). The UI draws them only on the built-in image (not a user's image): the knob image (`resources/knobs/knob.png`, pointing up), its body unrotated (a real knob's reflections don't turn with it) and its pointer, cut out of it, rotated to the value over the same 270 degrees as the panel's knobs, its lighting layer (`sheen.png`, turned into white with alpha = brightness, drawn unrotated at 20 %) over it, on a soft shadow; `tools/embed_knob_images.py` cuts both to the knob's circle into `src/ui/KnobImages.cpp`. In the block panel they're `Hit::Knob` areas for the slot's host parameters, so dragging, the wheel, MIDI learn and help work as on the panel's knobs and both show the same value. Since 2026-10-28 every pedal has a photo: each face also has a footswitch (`Hit::FaceSwitch`, toggles bypass like the tile's power button) and a rim colour: the knob is then the blue-rim knob (`resources/knobs/rim.png`), split like the LEDs into a neutral part and a colour part that is added tinted (`photoTint()`), with a blurred copy of the rim added as glow so it reads at a few pixels; a zero colour keeps the black knob.
- **Add Block → NAM / IR** lists the library: a favorites filter, a star per file, and Browse… for a file outside the library. The search box at the top of the dialog (focused when it opens, × to clear) searches every category: built-in blocks by name and category, library files by name, folder or metadata (all words must match). Results are listed under category headings.

## 7. User interface

- DPF UI with NanoVG drawing. Resizable, with HiDPI scaling. The default logical size is ~1200 × 720 and the minimum is ~900 × 560.
- Layout:
  - **Top bar**: the logo (two embedded layers, `resources/logo/`: the crop circle in white, tinted with the highlight colour, and the wordmark), preset menu and preset name, undo/redo, the update notice when a newer release exists (section 5); on the right, icon buttons for the GitHub link (the GitHub mark in outline; opens the project's page), the Fretbored link (the Fretbored app icon, drawn flat in the icon colour from its `assets/icon.svg`: faint strings and frets, the notes spelling an F as rings, the root's heavier, after Fretbored's Ring look, 2026-10-30), the metronome (with ▾ for its panel), the tuner, settings and global bypass.
  - **Middle**: the chain, left to right, with square block tiles and "+" boxes. A split shows as two rows that rejoin at the merge. Hovering the gap between two blocks shows two small buttons: insert a block there (upper half) and, with no split yet, split there (lower half). A chain wider than the window scrolls with the mouse wheel, a thin scroll bar under it, or a middle-drag anywhere over it but a block. Middle-clicking a block removes it (owner, 2026-10-24; it used to enable or bypass it). Double-clicking a block, or Replace in its right-click menu, opens Add Block on the block's own category and puts the new block in its place and slot (one undo step). The block menu: Enable/Bypass, Replace, Remove, Copy, Paste after (once a block is copied), MIDI Learn bypass (and Clear MIDI when mapped). Copy takes the block's type, settings, values, bypass and image, not its MIDI mappings; the copy is shared by the instances in the host's process, so it pastes into another instance too, and right-clicking a "+" box pastes at the end of that section (owner, 2026-10-29). A paste is one undo step and takes a free slot. The mouse wheel over any knob turns it (2% a notch, Shift 0.2%; a burst of notches on one knob is one undo step).
  - **Below the chain**: the selected block's panel: a large block image on the left (placeholder art until real pedal/amp/cab images exist), the name and file above the controls, and the generic controls centred in the space right of it in one or more rows, spread out up to 1.6x their cell width and 1.35x their row height to fill it (owner, 2026-10-28); dark gray while the block is bypassed. The image is meant to fill the panel's height (owner, 2026-10-25): the controls go into as many rows as needed (and as fit) for that, and the image only shrinks when even that leaves too little width. The generic knobs may later go away in favour of turning knobs on the image itself.
  - **Bottom bar**: mono/stereo toggle, input, bass, middle, treble and output knobs, input/output meters with clip lights (click to reset), limiter on/off.
- **Interactions**:
  - Drag a block to move it; drop indicators show where it lands.
  - Right-click a block: bypass, remove, copy, paste, MIDI learn.
  - Double-click a knob to reset it; Shift-drag for fine control.
- **Dialogs**: Add Block (categories on the left), Settings, and the Tuner and Metronome panels (overlays). Lists in dialogs (Add Block's blocks, library files and search results, the preset menu, Manage Presets, Save As's folders) show a scroll bar at their right edge when they're taller than their space, to drag or click for those without a scroll wheel (owner, 2026-10-25). Add Block's rows are tall enough to see the art (112 px for blocks, 76 px in lists).
- **Redraws on Linux**: X11 events are only read when the host calls the UI. LV2 hosts call it on their idle tick (Reaper: ~30-36 Hz), so dragging redraws at that rate. For VST3, a DPF patch (`patches/dpf/`) registers the X11 connection with the host run loop's event handler, so events are handled and redrawn as they arrive, whatever the host's timer rate. The UI turns vsync off for its GL window, so a buffer swap never stalls the host's GUI thread waiting for the screen. `XYTHOS_SHOW_FPS=1` in the host's environment shows a frame-rate readout.
- **Hover help**: resting the mouse on a control for 0.6 s shows a translucent popup with its name and a plain-English explanation of what it does and how to use it. The texts are in `src/ui/ParamHelp.cpp` (block controls by typeId and control name, the others by parameter symbol); `tests/ParamHelpTests.cpp` checks that every block control and every global control has one, at least 80 characters long. The top-bar icon buttons and the metronome's beat, grouping and tap controls have popups too, and so does every block type (`blockTypeHelp()`: what it is, what it's for, how and where to use it), on its tile in the chain and on its entry in Add Block (categories and search results).
- A dark theme defined as colour tokens in one file, so it can be restyled: the window shows the owner's background image (`drawBackground()`, scaled to cover); what the window shows in its base state (bars, panels, tiles, buttons, the tuner and metronome) is black at 50% with 1 px gray outlines (`surface()`), and everything that appears over it (dialogs, menus, help popups, the toast) black at 95% (owner, 2026-10-29; a blur behind the popups was tried and dropped), the items listed in Add Block black at 97%, and buttons that are on are an accent outline over a faint accent tint. Knobs: hairline body, 21 ticks lit up to the value, a dot for the position. Font: Jost Light (Regular for small text), drawn 1.69x the layout size because Jost runs small, with DPF's DejaVu as the fallback for glyphs Jost lacks (★, ▾).
- **Outlines, buttons, fills and knobs in ink**: with a gradient on, the highlight colour is painted with one window-fixed image paint instead of a solid colour (`XythosUI::inkPaint()`; the paint is mapped back through the current transform, so the colours stay put wherever a shape is drawn). The texture (`state/Ink.*`, 128x80 RGBA, stretched over the window) is made when the mode or the colours change: Smooth runs the colours left to right, slightly tilted; Splotchy is fixed two-octave value noise stretched to the full range, so the blobs look the same every time. The UI's `fillColor`/`strokeColor` shadow NanoVG's and route the highlight's RGB to the paint (alpha kept); dimmed (bypassed) colours stay grey. **Text is not painted**: NanoVG draws glyphs with its font atlas and the paint's colour alone, and an image paint's colour is white, so `text()`/`textBox()` draw ink text in its plain colour (seen in jalv on 2026-10-30; not yet tried in Reaper). Making text follow the gradient would need either a strip-by-strip scissor approximation (many draws, visible banding) or drawing text into an offscreen target and masking it, both larger changes. Colours are lifted toward white below relative luminance 0.12 (`ink::lighten()`). The picker is its own dialog over Settings (owner, 2026-10-30; replaced RGB sliders): a colour wheel drawn as 48 hue wedges with linear gradients under a radial grey-to-clear gradient (so each point is exactly that hue and saturation at the slider's brightness), a brightness slider, the colour's name (`ink::colorName()`: a hue name by angle with a shade from saturation and brightness; greys, browns, olives and peach are special), the hex value in a text field (select, Ctrl+C, the Copy button, or type: a full value moves the wheel, saved when the field is left), and the saved colours (`Settings::savedColors`). The wheel keeps its own HSV (`fPickHsv`) apart from the stored colour, which is lifted, so dragging stays smooth. The logo's crop circle is a separate white layer (`kLogoMark`) drawn with its paint's colour set to the highlight (`highlightAt()`: the texture's colour at the circle, or the accent).
- **Power LEDs**: every pedal shows an LED, lit with a glow while the block is on and dark while it's bypassed (or missing or not running), on its tile and in its panel (`drawLed()`). The drawn pedals have a red one beside the footswitch and the amps a pilot light; built-in images list theirs in `PedalFaces.cpp` (position, size and lit colour; on the photos, the indicator spot north of the footswitch, coloured like the glyph), and the UI draws over the image's own LED, so an image can show it lit or unlit. Add Block's thumbnails show none.
- The GitHub and Fretbored links open the browser through a small platform helper (`xdg-open` / `ShellExecute` / `open`). On a narrow window the preset button narrows (down to 160 px) so both links still fit; while a MIDI learn message shows in a window under 1200 px, they make room for it.

## 8. Build, test and release

- **CI** (GitHub Actions):
  - Linux and Windows builds of VST3 and LV2 on every push, and a macOS universal build (VST3, LV2, AU; ad-hoc signed, the AU checked with `auval`, tests run on arm64)
  - unit tests
  - plugin validation with pluginval (VST3) and lv2lint (LV2)
- **Unit tests**:
  - tuner accuracy
  - metronome sample timing
  - delay and reverb behaviour
  - chain build and state round-trips
  - preset embedding and missing files
  - zip scanning
  - undo/redo
- **Real-time check**: a test build that fails if the audio thread allocates memory.
- **Manual DAW testing**: Reaper first, on Linux and Windows (it's the DAW the project owner uses); Ardour and Carla on Linux as secondary checks.
- **Releases**: zip files per platform attached to GitHub Releases, tagged `vX.Y.Z` to match the `project(VERSION)` in `CMakeLists.txt` (the update check compares the two). Bump the version before tagging.

## 9. Performance targets

- An empty chain uses under 0.5% of one core at 48 kHz with a 64-sample buffer.
- Engine overhead around blocks stays under 5% of the blocks' own cost.
- Changing a model or editing the chain causes no dropouts or clicks.
- The UI opens in under 300 ms.
- A library rescan of 1,000 files with an existing index takes under 1 s.

## 11. Decisions log

1. **CPU baseline**: AVX2/FMA is required.
2. **Standalone app**: dropped for now; VST3 and LV2 only.
3. **Reverb types**: room, hall and plate.
4. **Test DAW**: Reaper is the primary host.
5. **Compressor**: added to M3, studio style (owner's choice over a simple pedal-style one).
6. **Theme**: no gradient; pure black window. Boxes were flat near-black gray at first; the owner then chose black boxes with hairline gray outlines, Jost Light and tick-scale knobs with a dot, from drafted screenshots (fonts, knobs and surfaces; 2026-10-22).
7. **Block panel**: large block image on the left, generic knobs centred in the space to its right (were right-justified until 2026-10-28).
8. **Folder choice**: DPF's file browser can't pick folders, so "Choose…" opens the system's folder picker (`src/ui/FolderPicker.*`, on its own thread): Linux tries the desktop portal (FileChooser v3, `directory`), then zenity, then kdialog; Windows uses IFileOpenDialog with FOS_PICKFOLDERS; macOS runs AppleScript's `choose folder` through `osascript` (its own process, so it needs nothing from the host's main thread). With none of these, it falls back to DPF's browser and takes the folder of any file picked in it. The path can also be typed or pasted.
9. **MIDI map in the chain state** rather than a separate plugin state, so it follows the chain's routes (including the exchange file for Reaper's LV2) and is covered by undo and presets.
10. **Metronome samples**: only the Classic clicks come from Fretbored. Its Digital samples carry a third-party artist credit (owner's call to remove them), so the Digital sound is generated in code.
11. **16 parameters per block** (was 8), for the Doppelganger Delay. Most host parameter indices moved, which was fine only because nothing was released yet; from v1.0 on the count is fixed.
12. **Pedals before v1**: the owner asked for a wide pedal set first (no rush to v1). Varieties are a Type choice inside one block rather than separate blocks; a released Choice list never changes (saved values would map to other choices), so new varieties that don't fit become new blocks.
13. **Pitch effects without latency**: delay-line pitch shifting with pitch-synchronous splices (polyphonic, clean on notes and most chords) instead of FFT or PSOLA methods that add latency; the synth, harmonizer and octave track pitch with YIN on a decimated copy (detection takes 4-24 ms, but adds no latency to the audio).
14. **Looper controls as momentary parameters**, so footswitches map to them with MIDI learn; the looper keeps one loop (60 s at 48 kHz).
15. **macOS** (owner, 2026-10-24; was out of scope): a universal binary (Apple Silicon and Intel), macOS 11+, VST3, LV2 and AU (Logic and GarageBand only load AU). Linux and Windows stay x86-64 only. No Developer ID yet: CI signs the bundles ad hoc (Apple Silicon won't load unsigned code), so downloads need `xattr -dr com.apple.quarantine`.

16. **Pedal photos embedded** (JPEG, WebP since 2026-10-28) (owner, 2026-10-28): every pedal has a photo with knobs, a power LED and a footswitch on its face. The images stay inside the plugin rather than in files beside it: at about 30 KB each (JPEG; 3.5 MB with thumbnails) they barely grow it, embedded data costs no RAM until read, and there's no resource folder to find or lose per format (VST3, LV2, AU bundles) or per host process. Only the JPEGs are committed; the build turns them into C++ (`cmake/EmbedBlockImages.cmake`). The UI decodes only what it shows, uses thumbnails for tiles and lists, and keeps at most four full-size images. Worth revisiting only if images grow to tens of MB (e.g. much higher resolution): then a resources folder in each bundle, read through DPF's `getResourcePath()`. 2026-10-28: doubled to 1280 px after the owner saw compression artifacts, and moved to WebP q96 (11 MB; the owner approved adding libwebp v1.6.0, decoder only; JPEG XL compresses a little better but its library is much heavier); still embedded.

17. **User images in the config directory, not sidecars** (owner, 2026-10-29): users add their own amp, cab and pedal images to libraries in the config dir (copied in, so they survive moving or deleting the original) and pick one per block, instead of an image file next to each NAM file or IR. Any block can have one, not only NAM and IR blocks. They're drawn as static images (no face knobs, LED or footswitch: those are placed for the built-in photos only), and a deleted image's blocks fall back to their stock look.

18. **Update notice, not self-update** (owner, 2026-10-29): the plugin only tells the user a new version exists and links to it. Replacing its own files from inside a DAW runs into locked binaries on Windows, admin-only install folders, several loaded instances and hosts, macOS signing and quarantine, and would make the plugin a channel for running downloaded code; an installer or update app outside the DAW is the place for that, if ever. The check is opt-out in Settings and sends nothing but the request.
19. **Renamed to Xythos** (owner, 2026-10-29; was NAMsayin; the repository too): the name, the developer shown in hosts (Xythos, was the owner's username), the bundles, the preset extension (`.xythos`), the config and cache folders and the LV2 URI (`https://github.com/singularity098/xythos`) all changed, with no migration (the owner moved their own files). The VST3 and AU IDs (brand `S098`, plugin `NMsy`) stay as they were: hosts never show them, and keeping them lets projects saved with the VST3 or AU find the renamed plugin. LV2 projects saved before the rename need the plugin re-added.
